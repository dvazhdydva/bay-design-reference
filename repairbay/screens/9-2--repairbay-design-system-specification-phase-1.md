REPAIRBAY / DESIGN SYSTEM

One operational interface.
Consistent in every detail.

Phase 1 · Repair-job card and core components · 04 November 2026
For review before extending the system to other screens.

01 / Scope and source of truth

Preserve the approved repair card: navy header, pale canvas, white bordered accordions, compact controls and four-stage repair workflow.

Included in this approval

Source audit; named tokens and Inter styles; button, field, status, selection, accordion, feedback and save variants; conditional IW/OOW/WEEE patterns; status icons; a fully editable repair-card example.

After approval

Active/archive lists, registration, Returns, shipment details, Spare parts and full add/edit/select modal templates. Do not extend unapproved refinements to these screens yet.

Sources

Approved repair-job-full.jpg; repository workspace.css, job-detail.html, repair-workspace.js and workspace-progress.js; established user decisions. No code or production changes are part of this Figma deliverable.

02 / Audit → proposed refinements

Priority is consistency, not a new visual direction. Changes below are proposals unless already agreed in the brief.

Field spacing

Inconsistent label gaps and section-specific overrides make controls appear misaligned. Standardise label → control to 6 px, vertical field gap to 14–18 px and column gap to 24 px. Keep 38 px controls.

Disclosure and vertical density

The reference shows a collapsed change-reason chevron while its textarea is visible. Document one disclosure state: hide the body when collapsed; reveal the existing reason field when expanded. Done sections auto-collapse on entry only.

Integration hierarchy

Existing fetch actions look alike and the external-form button is after its resulting number. Use source-colour fetch actions; put the form-fill action before the SO field in one subtle dashed group.

Table legibility

A twelve-column table is vulnerable to long serials, labels and status values. Keep all columns, fixed widths, short Docs label, icon selection/delete, 10-character description preview and keyboard-accessible expansion. Never shrink the entire table to unreadable text.

Feedback and disabled states

Explain why an action is unavailable next to it. Loading, validation and retry need text, not only colour. Preserve existing input on failure. Saved/Unsaved/Saving controls occupy a consistent area.

Destructive actions

Keep Delete repair below the histories with a divider and generous separation. The explicit destructive label and confirmation matter more than a large red surface.

Elevation

04 / Component contracts

Purpose, anatomy, dimensions, state variants and keyboard rules are also stored on reusable main-component descriptions.

Button

Label + optional 16px leading icon. 38px height, radius4, horizontal padding14. Primary, Secondary and Destructive each have Default/Hover/Focus/Disabled/Loading. Enter/Space activates. Labels describe actions, not vague confirmation. Icon-only buttons require accessible names and tooltips.

Field

Visible label + 6px gap + control + optional helper/error. Text/Date/Select/Textarea expose editable Label and Value. Default/Hover/Focus/Disabled/Read only/Error. Use native keyboard date/select behaviour in RB. Required and error states use words as well as colour.

Selection and table cells

Checkboxes use Space and clear focus. Only eligible free parts are selectable; confirmed order composition stays locked. Inline editors are keyboard reachable. Long descriptions show at most ten characters including the ellipsis; hover/focus reveals full text.

Accordion and progress

Header anatomy: chevron, section number, title, completeness badge, summary. Enter/Space toggles; expose aria-expanded. Done/In progress/Pending/Not started describe completeness, not outcome. Progress counts Done sections only.

Save controls

Saved disables Save/Discard; Unsaved enables them; Saving prevents duplicate submission. A failure keeps edits and explains retry. If further edits occur during saving, they remain unsaved rather than being overwritten.

Modal and tooltip

Modal heading and actions stay visible while the body can scroll. Trap focus; Escape/Cancel closes and restores focus to opener. No destructive confirmation on outside click. Tooltip supports keyboard focus and Escape, and must not be clipped by table overflow.

05 / Integrations and data mapping

Source badges indicate available fetch capability. They are not evidence that a stored value originated in that service.

GSPN unit fetch / blue

Targets: model derived from model code, model code, version, purchase date, warranty expiry. Use purchase date when present; otherwise suggest production date and warn. Warranty uses L. Preview Current/From GSPN/Status before Apply to form; replacing existing data requires a reason. Save stores and audits.

Simpro fetch / violet

Requires a non-empty original Simpro job. Job site = Site Custom → Store Name/ID; if empty use Site name. Fz = Customer. Received = date of the latest Work Note. Repair comments = Summary of Works Completed only. The Simpro job field is a manual lookup key, not a fetched target.

Parts / blue; IW claim / teal

Parts fetch requires a saved GSPN SO; it affects the parts table only. Claim fetch is a separate action affecting claim number and amount only. Automatic claim lookup remains unimplemented and disabled with an explanation. IW claim is a borderless footer shown for IW repairs only.

External SO form / dashed group

Fill GSPN service order form comes before the SO field within one dashed border. Available only while SO is empty. It prepares an external form for review; it does not automatically Save. Preserve user-controlled confirmation in GSPN.

06 / Repair business rules

Visual states reflect existing records; users must not choose an arbitrary icon to make the workflow progress.

OOW and WEEE

OOW shows Copy OOW details plus approver and approval date. Missing OOW approval outlines downstream blocks red; expired warranty outlines Unit details. WEEE requires approver, approval date and information source, then explicit outcome confirmation.

PO and parts

Create PO applies to free selected parts. Add to draft PO is disabled when no draft exists and offers draft selection when several exist. GSPN confirmation locks order composition. Remove only free/unordered parts. Bulletins remain linked by part number.

Completion and archive

Repaired, QC pass and WEEE require confirmation. Confirmation locks the repair; engineer/date are retained. Archive after seven days, preserving green Repaired, blue QC pass and red WEEE. A later repair is a new card and shows prior repair history.

DOA

DOA received is primary until a replacement draft PO exists. The user may order the replacement before shipping DOA. Outstanding DOA return remains a secondary warning until dispatched. Do not block replacement ordering on return shipment.

07 / Viewport and responsive rules

Target is a 1920×1200 physical laptop at Windows150%, browser100%: approximately1280 CSS px wide, with less height after browser chrome.

Desktop acceptance

Approval frame width1280; page gutters32; content1216; inner card1172. All twelve table columns fit within1172. Vertical scrolling is acceptable for the fully expanded reference. Progressive disclosure reduces routine page height; do not hide required fields or reduce body text to avoid every scroll.

Smaller screens

Mobile prioritises reading repair status and details. Complex editing and browser-bridge actions remain desktop-first. Full mobile operations are not part of phase1. Narrow layouts may use cards or deliberate secondary disclosure rather than shrinking the desktop table.

08 / Open decisions and implementation handoff

These are explicit limits, not completed functionality.

For approval

Confirm source tags and hover targeting; the 1280px table populated-state readability; icon distinctions at24px; compact button grouping. The attached source contains no IW claim, OOW or WEEE data; their components are conditional specimens, not changes to that source record.

Tool and phase limits

Courier is not installed in the Figma runtime. This draft supplies visual state variants and behaviour documentation; it is not a fully wired interactive application or tested browser implementation. Code Connect is not configured in the Thymeleaf repository. Remaining screen templates wait for approval.

Repository alignment

Source has hardcoded colours and dimensions rather than reusable CSS tokens. Proposed --rb-* code syntax on Figma variables documents the implementation contract; no claim is made that those CSS variables already exist. Adopt them in a separate implementation task after approval.
